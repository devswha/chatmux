# ultragoal: `record-review-blockers` creates an unbounded recursive goal chain (2.89B tokens burned over 6.5 days)

## Summary

`recordUltragoalReviewBlockers()` appends a new goal on every review blocker with **no dedup, no chain-depth cap, and no total-goal cap**. Because a blocker goal can itself be review-blocked, each block spawns the next goal indefinitely. Combined with the runtime `ask` block and the runtime `pause` block, an Ultragoal run has no reachable termination state when reviewers keep returning findings.

Observed on `gjc 0.12.5` (latest release), Linux x64.

## Impact

A single project burned **2,890,811,435 tokens across 24,772 LLM calls in 6 days 13 hours**, producing 9,314,032 output tokens (0.3%). 94.1% was `cacheRead` — the same context replayed thousands of times. One session ran **48h54m** unattended; the final session ran **7h15m** overnight and completed 0 goals.

## Root cause

`packages/coding-agent/src/gjc-runtime/ultragoal-runtime.ts:3883-3915` (main @ v0.12.5):

```ts
export async function recordUltragoalReviewBlockers(input: {...}): Promise<UltragoalPlan> {
	const objective = input.objective.trim();
	if (!objective) throw new Error("record-review-blockers --objective is required");
	const plan = await checkpointUltragoalGoal({ ..., status: "review_blocked", ... });
	...
	const nextId = `G${String(plan.goals.length + 1).padStart(3, "0")}`;
	plan.goals.push({
		id: nextId,
		status: "pending",
		steering: { kind: "review_blocker", blockedGoalId: input.goalId },  // chain link
	});
	await appendLedger(input.cwd, { event: "review_blockers_recorded", goalId: input.goalId, blockerGoalId: nextId });
}
```

The only validation is the empty-objective check.

### The sibling function has the guard; this one does not

`recordReviewFindingGoals()` (same file, line 4254) dedupes via `findOpenReviewBlockerGoal()`:

```ts
const existing = findOpenReviewBlockerGoal(plan, finding.message);
if (existing) { ...; continue; }
```

`recordUltragoalReviewBlockers()` never calls it. The CLI verb `record-review-blockers` — the one SKILL.md instructs agents to use — routes to the unguarded function.

Ledger events disambiguate which path ran: the guarded function emits `blockerGoalIds` (array), the unguarded one emits `blockerGoalId` (scalar). Affected sessions show only the scalar form.

### No caps exist anywhere in the file

Identifier sweep of `ultragoal-runtime.ts` @ main:

```
maxGoals 0   MAX_GOALS 0   goalLimit 0   GOAL_LIMIT 0
maxDepth 0   MAX_DEPTH 0   chainDepth 0  blockerDepth 0
maxBlocker 0 MAX_BLOCKER 0 tooManyGoals 0 depthLimit 0
```

All five `goals.length` references are ID generation or count display.

### Contrast with ralplan

`ralplan-runtime.ts` @ main carries 7 convergence guards (`iterationLimit`, `laneLimit`, `laneBudgetDecision`, `parseMaxIterationsValue`, `parseMaxReviewPassesPerLaneValue`, `parseMaxReviewPassesPerLaneSettings`, `reviewBudgetWarning`) — landed by #3356 "ralplan infinite-loop convergence".

`ultragoal-runtime.ts` @ main carries 1: `nudgeBudget` (ask-retry counter, unrelated to goal creation). Goal-creation caps: **0**.

The same class of defect was fixed in ralplan and left open in ultragoal.

### No escape hatch

`src/defaults/gjc/skills/ultragoal/SKILL.md`:

- L125 — `**Never pause.** ... record-review-blockers` **`and keep scheduling the next goal.`**
- L128 — `goal({"op":"pause"})` is **blocked at runtime** while an Ultragoal run is active
- L298 — While an Ultragoal run is active, the `ask` tool is **blocked for all agents**

So: cannot ask, cannot pause, must keep scheduling, and scheduling is unbounded.

```json

```

## Expected behavior

A review-blocker chain must converge or hand control back to the user. Unbounded growth of a metered-cost loop with no user-reachable stop is never an acceptable terminal state.

## Suggested fix

At `ultragoal-runtime.ts:3902`, before `plan.goals.push()`:

1. **Dedup** — call the existing `findOpenReviewBlockerGoal()`; return the existing goal instead of appending. Consider normalized/fuzzy matching, since findings are LLM-authored prose and exact `trim()` equality rarely matches.
2. **Depth cap** — walk `steering.blockedGoalId` back to the root; refuse beyond a configurable depth (default ~3).
3. **Terminal handoff on cap** — on refusal, auto-record `classify-blocker --classification human_blocked` so `goal({"op":"pause"})` becomes reachable, and surface `next_action: "resolve-blockers"` to the user rather than appending goal N+1.
4. **Reject forced `blocked → active` reconcile** for ultragoal, or require explicit user confirmation.

A budget warning analogous to ralplan's `reviewBudgetWarning` would also make the runaway visible before it becomes expensive.
